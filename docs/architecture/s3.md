# S3: профили, объекты и multipart (T11–T13)

## Профили и безопасность

AWS SDK v3 (`@aws-sdk/client-s3` 3.1126.0) используется только main process.
Одна форма поддерживает AWS (пустой endpoint) и S3-compatible root endpoints, region,
bucket либо список buckets, начальный prefix и path-style/virtual-hosted addressing.
Начальный prefix задаётся вместе с bucket. Endpoint должен использовать HTTPS; HTTP
разрешён только для localhost/loopback fixtures. Отключения проверки сертификата нет.

Access key ID является metadata профиля. Secret access key и optional session token
сохраняются одним encrypted JSON blob через существующий CredentialService/safeStorage.
Их нет в React state, snapshot-ответах и открытом SQLite. Пустые поля при редактировании
сохраняют прежние значения; отдельный checkbox явно удаляет session token.
AWS credential chain и переменные окружения не подставляются вместо указанного профиля.

Проверка подключения выполняет только ListObjectsV2 (один объект) или ListBuckets,
без записи и удаления. Повторная команда проверки действительно обращается к серверу.
Для bucket-профиля необходим s3:ListBucket; режим всех buckets требует s3:ListAllMyBuckets.
DNS, TLS, endpoint/region, authentication, permissions и transient I/O имеют безопасные
локализуемые ошибки, без текста SDK, подписанных HTTP-запросов или credentials.

## Пути, листинг и операции

Расширения контрактов обратно совместимы: S3 profile получает optional initialPrefix,
FileSystemEntry — optional s3Kind/versionTag, ProviderOperationOptions — optional versionTag,
WriteOptions — optional expectedSize. VersionTag обозначает identity для условного чтения,
не универсальную checksum. Добавлены строго перечисленные действия существующего
workspace IPC; произвольные SDK options и отключение TLS не проходят Zod-валидацию.

Доменный путь сохраняет пару bucket + key. Строка панели `s3://bucket/key` использует
покомпонентное percent-encoding. Преобразования не используют URL/path normalization:
повторные `/`, `.` и `..` не схлопываются. Ограничение ключа проверяется как 1024 UTF-8 bytes.
При скачивании ключи, которые невозможно безопасно представить локальным именем,
отклоняются, а не переименовываются молча.

Листинг последовательно читает все страницы с continuation tokens и защитой от
повторяющегося token. UI явно обозначает Bucket / Prefix / Object. Prefix — виртуальный
каталог; trailing-slash marker рассматривается как prefix по соглашению S3-browser.
Zero-byte object без завершающего `/` остаётся обычным объектом. Bucket нельзя удалить,
переименовать или создать через файловые команды этой версии.

`trueDirectories`, `permissions`, `symbolicLinks`, `atomicRename`, `resumeWrite` — false.
Поддерживаются stat/head, marker creation, copy, delete, rename, streaming read/write,
server-side copy, multipart upload и resumeRead.

Перед удалением main вычисляет manifest-снимок: точные keys, размеры и ETag.
Пользователь видит количество объектов (включая marker) и общий объём. Подтверждение
привязано к manifest; изменение списка/размера/ETag требует нового расчёта. Удаляются
только подтверждённые keys, не произвольный актуальный prefix; перед каждым DELETE выполняется
повторный HEAD и передаётся If-Match. Это **не транзакционная гарантия**: проверенный MinIO
игнорирует условие DELETE, поэтому замена key между последним HEAD и DELETE может быть удалена.
Подтверждение явно предупреждает остановить конкурирующих writers. Для versioned
buckets удаление текущего объекта может создать delete marker; полное удаление истории
версий и Object Lock не поддерживается.

Rename явно показан как неатомарный copy + delete. Сначала копируются все объекты, затем
условно удаляются оригиналы. Нет автоматического rollback/повтора разрушительного этапа:
ошибка может оставить оба имени или частично обработанный prefix. Источник копируется
с CopySourceIfMatch. Базовые HTTP metadata и пользовательские metadata сохраняются;
ACL, tags, версии и специфические параметры шифрования не клонируются как отдельная модель.

Проверенный MinIO игнорирует If-None-Match назначения обычного CopyObject. Поэтому copy
без overwrite использует server-side UploadPartCopy + conditional CompleteMultipartUpload;
нулевые объекты — conditional PutObject. Обычный CopyObject применяется только при явно
разрешённом overwrite и размере до 5 ГиБ. Большая server-side copy тоже использует multipart.
Для защиты назначения используется conditional Put/Complete; unsupported не заменяется
опасным delete + write. Условный DELETE поддерживается не всеми backend, см. предупреждение выше.
MinIO-ограничения ключей `//`, `.` и `..` показываются как ошибка;
unit-тест отдельно подтверждает, что на стороне клиента ключи не нормализуются.

## Передачи, память и целостность

SFTP и S3 используют одну очередь, progress, speed/ETA, cancel/retry и политики
ask/overwrite/skip/rename. Каждая рабочая вкладка имеет отдельный provider instance.
Файловые mutations и cleanup не запускаются поверх активной передачи этой сессии.

S3 upload публикует конечный key только при успешном PutObject/CompleteMultipartUpload,
без промежуточного видимого объекта и последующего rename. Multipart начинается с 8 МиБ,
одновременно отправляются максимум две части, входные чанки Transfer Engine — 64 КиБ.
Для крупных файлов размер части увеличивается до лимита 10000 частей, максимум 64 МиБ;
файлы сверх этого бюджета явно отклоняются. Память зависит от размера/числа частей, не файла.

Перед финализацией проверяются ожидаемый размер и неизменность локального источника.
Каждая часть/небольшой PutObject передаёт Content-MD5 для серверной проверки транспорта.
ETag считается opaque identity, **не** MD5 полного multipart-файла. Download использует
поток GetObject, запрашивает доступные checksum через ChecksumMode и проверяет число байтов.
Range читается с If-Match. SDK проверяет поддерживаемые возвращённые checksum; отсутствие
checksum у backend не подменяется вычислением MD5 из multipart ETag.

Download resume возможен только для той же операции в текущем процессе: совпадают size,
mtime, ETag и SHA-256 всего сохранённого локального префикса. Изменение запрещает resume.
Upload resumeWrite не объявляется: незавершённый multipart отменяется, retry начинает
загрузку с нуля; отдельные HTTP/part requests имеют ограниченные SDK retries.

## Долговременная очистка

SQLite migration v3 добавляет multipart_cleanup (profile, bucket, key, upload ID).
Upload ID записывается сразу после CreateMultipartUpload и до отправки частей.
Успешный complete/abort удаляет запись. При отмене ожидаются все in-flight части,
затем abort выполняется с отдельным, не отменённым signal. Неудачная очистка остаётся
в SQLite и видна после рестарта; UI позволяет повторить её. Активные multipart-записи
не показываются как требующие ручной очистки до завершения операции.

Нельзя удалить или изменить профиль с ожидающей очисткой: это потеряло бы endpoint или
credentials для abort. После рестарта ничего разрушительного автоматически не выполняется.
Неопределённый результат самого CreateMultipartUpload (ответ с ID не получен) невозможно
восстановить по ID на клиенте; для production buckets рекомендуется серверная lifecycle
очистка abandoned multipart. Восстановление очереди с явной проверкой реализовано в T14;
см. `commander-recovery.md`.

## Проверки и границы

Проверены MinIO, общий provider contract с S3-exceptions, Unicode/pagination, read-only
credentials, конфликты copy, prefix delete preview, 256-МиБ multipart roundtrip, отмена,
transient retry, Range resume, несовпадение ETag, persistent cleanup и секреты/token.
Финальный интеграционный прогон 2026-09-04: прирост peak RSS при 256-МиБ S3 roundtrip около 78 МиБ,
автоматический бюджет — менее 192 МиБ сверх baseline тестового процесса.
Это не измерение суммарной памяти всех процессов Electron.

Electron E2E проверяет две S3-сессии вместе с одной SFTP, реальные profile encryption,
upload/download, copy/rename, preview/delete и повторное подключение после рестарта.
AWS-аккаунты в тестах не используются; совместимость с реальным AWS следует из SDK/API,
но live AWS acceptance не выполнялся. CI настроен для этого integration suite; hosted CI
в ходе задачи не запускался. SFTP ↔ S3 и восстановление очереди реализованы в T14;
дополнительные проверки описаны в `commander-recovery.md`.
